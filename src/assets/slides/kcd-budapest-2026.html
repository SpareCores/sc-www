Our main goal is to stop cloud waste, and while there are many ways to do this, some even works, such as:

  • identifying idle resources
  • automatically scaling down resources when they’re not needed
  • deleting unused resources or migrating e.g. to cheaper storage tiers etc

We focus on:

While pretty much everyone understands that cloud is still just another computer, at a remote location, that I can spin up quickly and throw away as needed, BUT we often don’t really know what kind of computer that is.

Before the cloud, you could simply walk to the server, and it was not too difficult to say that the computer running your program

  • is a potato
  • or a commodity PC with a case that has started turning yellow over the years
  • or it’s a bleeding edge, high-end server
  • or not so new and it still has a turbo button

You could even open up the case when the system administrator was not watching …

BUT nowadays

Like what on earth is even a virtual CPU?! Right?

There’s a conceptual uncertainty and massive visibility problem here, as a vCPU could range from an overprovisioned, poor-performing thread with saturated bandwidth to memory, versus a dedicated CPU core of a state-of-the-art server – with massive CPU cache and high memory bandwidth.

Which means that your applications could run much much faster!

A: GIL history — for folks who don’t know the GIL yet
- image: G(H)uido v(F)an Rossum + Larry Hastings (Gilectomy)
- GIL since early 90s · serializes Python bytecode · more cores ≠ faster for pure Python
- Greg Stein 1996 patch · parts landed, GIL stayed
- Gilectomy (Larry Hastings, ~2016): real PoC, fine-grained locks — overhead killed it (Guido: no single-thread regression)
- Sam Gross nogil → PEP 703 (2023): optional free-threaded build
- 3.13 experimental · 3.14 officially supported, not default · 3.15 Stable ABI abi3t
- for GILty-class apps: promising if you redesign for threads + deps support · else still need fast single core
- working name for this project: “Core Alone” — fits, right?

Pub talk → need benchmark-ranked types in Karpenter (incl. EKS Auto)

Plan (sc-karpenter-nodepool ADRs + sequenced v1 plans):

  1. Own NodePools only — never patch user pools / no NodeOverlay
    → managed Karpenter + GitOps (Argo CD, …) — no fights over a shared object
  2. SCNodePool → one NodePool — template verbatim + selected instance-type list
  3. Emit universal keys only (instance-type · arch · capacity)
    → avoid RequirementsDrifted loops
  4. Selectors + ranking from Keeper (e.g. PassMark ST · family band)
  5. Churn control — 24h refresh · hysteresis · never empty list
  6. Go / kubebuilder — reuse Karpenter validation + provider test fakes

A: how we designed it (with Claude)

  • problem: Karpenter has shape + price, not measured single-core
  • constraint: EKS Auto Mode → can’t fork Karpenter / patch their pools
  • also: GitOps (Argo CD, …) — don’t mutate a pool the user owns → sync wars
  • ADR-001: create our own NodePools only
  • ADR-003: one SCNodePool → one NodePool
  • ADR-004: only stamp keys every provider accepts — else drift loop
  • ADR-002: read Keeper API, filter/rank client-side
  • ADR-006: churn — don’t replace nodes every time the ranking wiggles
  • ADR-007: Go so we import Karpenter’s own validators
  • plans 01→08: scaffold → selection → adapters → controller → tests → Helm

Limitations (vs “pod annotation → any cloud / region / AZ / SKU”):

  • not a provisioner — only writes a Karpenter NodePool (instance-type list)
  • one cloud · one cluster — regions from NodeClass / node labels, not per-pod
  • no cross-cloud / cross-region hop in one request (AWS≠GCP≠Hetzner from one Pod)
  • needs Karpenter + cloud provider already there (EKS / Auto · AKS NAP · GKE · …)
  • no VPC / image import / Flatcar join / mesh — that’s not this controller
  • Pod can pin a type (node.kubernetes.io/instance-type) — but only if it’s already in the pool
    · no “any vendor · any region · this SKU” from one annotation (≠ start.yml)

  • dream: Pod asks for exact type (and cloud/region) → node appears → isolate → tear down
  • yes, Pod can use nodeSelector / affinity on instance-type — Karpenter will prefer/launch that
    · if that type is in the generated NodePool (SC selection / ranking)
  • no: one Pod cannot jump to another cloud/region — pool is still this cluster’s provider
